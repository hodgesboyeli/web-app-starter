# Web app starter

Minimal Next.js, TypeScript, Drizzle, Neon, and Vercel starter. This repository is a **GitHub template**: each app gets its own repository, Neon project, and Vercel project. The page is intentionally just a placeholder.

## Start your first app

1. On GitHub, select **Use this template → Create a new repository**. Give the new app its own name and clone that new repository. Its `main` branch is production. Do not keep working in this template repository.
2. In the new repository, run `npm ci` and `npm run build`. The local build does not need a database. Keep the repository private unless you intend to publish its code. If your GitHub plan supports branch protection for this repository, set `main` to require a PR before merge. GitHub Free can enforce this on public repositories, but not private ones; for a private Free repository, follow the PR-only rule yourself. If you are the sole maintainer, do not require an approving review: GitHub does not let a PR author approve their own PR. Codex must wait for your review and never merge or enable auto-merge without your explicit approval. Once you approve a specific PR and instruct Codex to merge it, Codex may merge it; you may also merge manually. Repository rules do not transfer from this template.
3. Create a **new Vercel Hobby project for this app** from the new GitHub repository. Set `main` as its production Git branch and keep the Next.js framework preset. If Vercel starts a build immediately, it may fail because the database is not connected yet; finish the checks below before redeploying.
4. In that Vercel project's **Storage** area, add **Neon** on its Free plan and create a **new Neon resource for this app**. Connect the resource to this Vercel project for Production and Preview. In the resource's project connection settings, set **Require Active Resource Before Deploy** to **Required** and **Create Database Branch For Deployment** to **Preview** only. The Neon project's default `main` database branch serves Production; each feature preview gets a child branch. Do not reuse another app's Neon resource or project. See [Neon's Vercel-managed integration guide](https://neon.com/docs/guides/vercel-managed-integration#enable-automated-preview-branching-recommended).
5. **Before the first successful production deployment, inspect Vercel's Production environment:** `DATABASE_URL` (pooled) and `DATABASE_URL_UNPOOLED` (direct) must both refer to this app's Neon production branch. Copy only the hostname from the **direct** Production URL (for example, `ep-...neon.tech`, without scheme, user, password, or database name) into a Vercel environment variable named `PRODUCTION_DATABASE_HOST` for **both Production and Preview**. Confirm the Production URL matches it and remove any manually set Preview database URLs that could override Neon. Only then redeploy `main`. The build fails closed if the URLs or host setting are missing or misrouted. If you already created a Neon project outside Vercel, use the [Neon-managed integration](https://neon.com/docs/guides/neon-managed-vercel-integration) to link that project instead; configure its preview branching and wait-for-resource settings before deploying. Use one integration path per app.
6. Deploy `main`. Confirm the Vercel production deployment is ready and its Neon target is the production branch. Then create a descriptive feature branch from updated `main`, push it, and verify Vercel gives it a preview URL and Neon creates a different branch. Test on that URL. Codex opens a PR and waits for your review; after you explicitly approve that PR and instruct Codex to merge, it may merge and must verify the production deployment and any migration. You may also merge manually. See [RELEASE.md](RELEASE.md) for the release and failure procedure.

This starter has no API keys, connection strings, project IDs, or app data. Keep `.env.local`, `.vercel/`, and `.neon` untracked. Never put database URLs in `NEXT_PUBLIC_` variables. The Neon integration supplies deployment secrets; no GitHub Actions secrets or deployment token are needed.

## Build and migrations

| Command | Purpose |
| --- | --- |
| `npm ci` | Install the locked dependencies. |
| `npm run build` | Build locally without touching a database; on Vercel, migrate the selected Neon branch first, then build. |
| `npm run typecheck` | Check TypeScript. |
| `npm run test:db-target` | Test the deployment database safety check using synthetic URLs. |
| `npm run db:generate -- --name=add_example_table` | Generate a versioned SQL migration from exported tables in `src/db/schema.ts`. Review and commit the SQL and Drizzle metadata with the code. |
| `npm run db:migrate` | Apply pending migrations to the branch named by `DATABASE_URL_UNPOOLED`. Requires the matching pooled `DATABASE_URL` as a safety check. |

Only change the schema file and generate a migration when the database structure changes. Do **not** add a migration for code-only features. Do not use `drizzle-kit push` against deployment databases. For a local migration test, put the two URLs of a disposable Neon branch in an untracked `.env.local` (see `.env.example`), then run `npm run db:migrate`. Never use production credentials for local experiments.

The Vercel build runs `db:migrate` before `next build`. Before opening a database connection, it checks that the pooled and direct URLs identify the same branch, that Production uses `PRODUCTION_DATABASE_HOST`, and that Preview uses a **different** endpoint. A missing or wrong host, migration error, or build error stops deployment. Drizzle records applied migrations in each database's `drizzle.__drizzle_migrations` table, so repeated builds skip completed migrations. A new app with no schema changes has an empty migration journal. Add tables only when your app needs them. The hostname check depends on setting `PRODUCTION_DATABASE_HOST` correctly for each app; verify it during setup and after changing the production Neon compute endpoint.

**Data rule:** Ordinary additive migrations, such as adding a table or nullable column, preserve existing production records. Never replace production with a preview branch. Deleting or substantially transforming existing data needs a separate reviewed release plan with backup, compatibility, and rollback steps. Neon preview branches can initially contain copies of production data; if an app holds sensitive personal or patient information, do not use this default preview setup until a safe test-data design is in place. Use synthetic or sanitized data in an isolated preview source.

## Feature flow

Update `main`, create `feature/describe-change`, commit and push. Vercel builds a preview using an isolated Neon branch; any committed migration runs there. Test the preview URL and inspect the Neon branch. Codex opens a PR and waits for your review; it never merges or enables auto-merge without your explicit approval for that PR. Once you approve it and instruct Codex to merge, it may merge and must verify the production deployment and any migration. You may also merge manually. Merge one PR at a time and verify production before merging the next. Delete the feature Git branch after release so preview branch cleanup can run. See [AGENTS.md](AGENTS.md) for the rules Codex should follow in each generated app.
